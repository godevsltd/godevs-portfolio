# Performance — GoDevs Portfolio

Performance is a foundation-phase requirement. The v0.1 theme is
built to keep LCP below 2.5s and TBT below 200ms on a fast 3G
profile with the default front-page and no plugins. This document
explains the design choices that achieve that target and the
budgets future phases must respect.

---

## 1. Targets

The v0.1 targets, measured against the default front-page with no
plugins and a 1MB hero image:

| Metric | Target | Measurement |
|--------|--------|-------------|
| Largest Contentful Paint (LCP) | < 2.5s | Lighthouse, fast 3G, mobile |
| Total Blocking Time (TBT) | < 200ms | Lighthouse, fast 3G, mobile |
| Cumulative Layout Shift (CLS) | < 0.1 | Lighthouse, fast 3G, mobile |
| First Contentful Paint (FCP) | < 1.5s | Lighthouse, fast 3G, mobile |
| Time to First Byte (TTFB) | < 600ms | Server-side, fast 3G |
| JavaScript payload | < 2 KB compressed | Theme JS only (WP core not counted) |
| CSS payload | < 30 KB compressed | Theme CSS + theme.json-generated |
| Font payload | < 100 KB compressed | Self-hosted latin subset |

The v0.5 target (Phase 11) tightens LCP to < 2.0s and TBT to < 100ms.

## 2. Design choices that enable the targets

### No external requests
The theme makes zero external requests at install, activation, or
during normal page rendering. No Google Fonts CDN, no jQuery CDN,
no analytics CDN, no third-party CSS or JS. Every asset is bundled
inside the theme directory and served from the WordPress install.

### No jQuery
The theme's `functions.php` does not enqueue jQuery. WordPress
core may load jQuery on pages that need it (e.g. pages with
certain core blocks like galleries with lightbox), but the theme
itself adds no jQuery dependency. `navigation.js` is plain ES5-
compatible vanilla JS.

### Deferred JavaScript
`navigation.js` is enqueued with `strategy: "defer"` and
`in_footer: true`, so it does not block render and runs after the
DOM is parsed.

### Self-hosted fonts
Inter and Newsreader woff2 files are bundled in `assets/fonts/`.
`@font-face` declarations in `theme.json` reference these files
via `file:./assets/fonts/<file>.woff2` URIs. Three weights are
preloaded via `<link rel="preload">` for LCP optimisation.

The latin subset is used (English-only content in v0.1); each woff2
file is ~24 KB. Total font payload is ~168 KB uncompressed, ~80 KB
compressed.

### Minimal JavaScript
The only JS file is `navigation.js` at ~1.4 KB uncompressed. No
third-party JS libraries are bundled. No runtime dependency.

### theme.json-generated CSS
The bulk of the front-end CSS is generated by the WordPress style
engine from `theme.json`. The CSS is inlined in the page head as
a single `<style>` block. There is no separate `style.css` to
load.

### Editor-only CSS in separate file
`editor.css` is loaded only in the block editor and Site Editor,
not on the front-end. This keeps editor affordances out of the
front-end payload.

### Print CSS only on print
`print.css` is loaded with the `print` media type, so browsers do
not fetch it until the user prints. (Modern browsers defer fetch
of `media="print"` stylesheets until needed.)

## 3. What the theme does NOT do (yet)

For transparency, the following are scheduled for Phase 11 and are
not implemented in v0.1:

- Critical CSS extraction (above-the-fold CSS inlined, the rest
  deferred).
- JavaScript splitting (the theme has one JS file, so splitting is
  not applicable yet).
- Variable fonts (the theme uses static woff2 files; variable
  fonts would reduce total payload if multiple weights are
  needed).
- Image format optimisation (the theme relies on WordPress core's
  default `srcset` and `sizes` attributes; WebP/AVIF depend on
  user-uploaded image formats).
- CDN integration (the theme has no CDN dependency; users can add
  one via plugin if needed).

## 4. Anti-patterns the theme avoids

### Render-blocking resources
The theme enqueues zero render-blocking resources. The deferred
`navigation.js` is the only theme-owned JS. `theme.json` CSS is
inlined in the head, not loaded via `<link>`.

### External DNS lookups
The theme does not introduce any external DNS lookup. Every asset
is served from the WordPress install's domain.

### Render-blocking fonts
Fonts are loaded with the default `font-display: swap` behaviour
from `theme.json` fontFace declarations. Three weights are
preloaded, but the preload uses `<link rel="preload">` (not
`<link rel="stylesheet">`), so it does not block render.

### Synchronous inline scripts
The theme has no synchronous inline scripts. The only inline JS
is the `wp_head` action's preconnect / preload hints (which are
HTML, not JS).

### Layout shift
Images use `aspect-ratio` to reserve space before load.
`theme.json` typography uses `fluid` font sizes with min and max
bounds, so text does not re-flow on viewport resize. The header
is sticky via CSS `position: sticky` (no JS scroll handler that
could shift content).

## 5. Asset loading strategy

### CSS
- `theme.json` → style engine → inline `<style>` in head.
- `editor.css` → enqueued only in editor (`enqueue_block_editor_assets`).
- `print.css` → enqueued on front-end with `media="print"`.

### JS
- `navigation.js` → enqueued on front-end with `strategy: "defer"`
  and `in_footer: true`.

### Fonts
- `@font-face` declarations in `theme.json` → style engine →
  inlined in head.
- Three weights preloaded via `<link rel="preload">` in
  `functions.php`.

### Images
- No theme-bundled images in v0.1 (user provides images via the
  Site Editor).
- WordPress core handles responsive `srcset`, `sizes`, lazy
  loading, and image format negotiation.

## 6. Caching strategy

The theme uses `filemtime()` for asset versioning in
`functions.php`. This ensures cache-busting when files change
without requiring a manual version bump. A CDN or page caching
plugin can safely cache theme assets indefinitely; the cache key
changes when the file changes.

## 7. Future performance work (Phase 11)

- Audit `theme.json` for unused style declarations; remove
  declarations that do not affect any block on the default
  front-page.
- Audit `navigation.js` for code that could be removed or
  replaced with CSS.
- Audit the bundled font subsets; consider adding the `latin-ext`
  subset if non-English content is common.
- Add a Critical CSS extraction step (potentially via a WordPress
  plugin; the theme itself should not ship a critical CSS
  implementation).
- Add a no-external-requests automated test in `/tests/`.

## 8. Performance measurement

The v0.1 theme is measured using:

- **Lighthouse** — Chrome DevTools, mobile, fast 3G profile,
  applied to the default front-page with a 1MB hero image and no
  plugins.
- **WebPageTest** — multiple locations, multiple devices, with
  the same setup.
- **Server-side TTFB** — measured via the WordPress REST API
  `/wp-json/` endpoint as a proxy for PHP response time.

Phase 11 will add an automated performance regression test that
runs Lighthouse in CI and fails if any metric regresses beyond a
configurable threshold.

## 9. Performance budget

Any PR that adds to the following budgets must explain why:

| Item | Budget | Current (v0.1) |
|------|--------|----------------|
| Front-end JS files | 1 file, ≤ 2 KB | 1 file, 1.4 KB |
| Front-end CSS files (non-theme.json) | 1 file (print) | 1 file |
| Font weights (per family) | ≤ 4 weights per family | Inter: 4, Newsreader: 3 |
| Font subsets | ≤ 2 subsets per family | Latin only (1 subset) |
| External requests | 0 | 0 |
| Inline CSS (theme.json-generated) | ≤ 30 KB compressed | TBD (Phase 11 measurement) |
| Inline `<script>` | 0 | 0 |
| `<link rel="preload">` | ≤ 3 | 3 |
